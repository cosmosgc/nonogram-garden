# 06 — Quality, security, and operations

**Goal:** Meet release-quality expectations across authorization, accessibility, performance, privacy, deployment, and recovery. These tasks apply throughout implementation; complete all applicable items before public launch.

## A. Security and privacy

- [x] Review every write route for authentication, policy authorization, Form Request validation, CSRF/session behavior, rate limits, and mass-assignment safety. The route inventory confirms state-changing routes use Laravel's `web` middleware (session and CSRF), account-backed writes require authentication, guest game-session writes are intentionally session-scoped, and every write route is throttled. Inputs are validated through Form Requests or endpoint-specific validation; object writes use policy/gate or moderator/admin checks; controllers assign only validated or server-derived fields, while privileged moderation uses explicit `forceFill`. Ownership, forged identity, and abuse limits have feature coverage.
- [x] Review every public response, Inertia prop, HTML page, API response, log, and cache entry for solution leakage and private data exposure. Public puzzle HTML/JSON, player progress responses, completion failures, local recovery payloads, game-session/life responses, profile output, and account export are covered; life checks return remaining lives without a correctness flag or canonical answer, while selected start-hint lines and intentionally public sanitized avatar images are documented partial disclosures. A repository-wide log/cache inventory found only the boolean pending-discovery setting cached; it is invalidated on update. Error-report channel failures use redacted records and never fall back to Laravel's unredacted exception report; regression tests cover the fallback.
- [x] Implement safe plain-text or sanitized Markdown rendering for user-authored descriptions; test stored/reflected XSS payloads. Descriptions render as escaped plain text; an HTML/JSON XSS regression test is included.
- [x] If image upload is added: enforce content sniffing, allowed MIME/extension, byte and pixel limits, safe decoding, metadata stripping, private storage defaults, and cleanup policy. The optional avatar upload accepts matching JPEG/PNG/WebP content and filename extensions up to 2 MB and 1024 × 1024 pixels, decodes and re-encodes to metadata-free PNG, stores only that sanitized derivative on the public disk because profile avatars are intentionally public, and removes replaced/account-deleted files. No source image is retained.
- [x] Add rate limits for draft creation/saves, uniqueness work, image operations, progress writes, and browse/search endpoints. Draft reads/writes, registration, login attempts, password-reset email requests, publish uniqueness checks, profile mutations (including avatar uploads), collection reads/writes, progress reads/saves, completion, game-session setup/mode changes/life checks/restarts, public profiles/browse/detail pages, moderation, logout, and account exports are throttled. The named application limiter keeps each route in its own per-user or per-IP bucket so an action on one endpoint cannot unexpectedly consume another endpoint’s quota. Puzzle image conversion remains browser-local; avatars are the only image upload and use the profile limiter. No unthrottled server image processing remains.
- [~] Document retention/deletion behavior for puzzles, progress, profiles, and optional source images; implement account data export/deletion before launch. A verified user can download a private, no-store JSON export containing profile data (including the avatar path), owned drafts/revisions (including their own solutions), saved progress, and collections. Account deletion cascades owned puzzles/revisions, collections, and dependent progress and removes the public avatar; tests verify this. Backup retention/erasure timing and final policy/legal approval remain unresolved.
- [x] Add moderation state independent from lifecycle/visibility, plus a privileged admin control for the pending-public preview. Publishing enters `pending`; a verified moderator/admin can approve, reject with a required note, or remove. Pending puzzles are hidden by default; an admin may expose only pending, public, published puzzles site-wide. Private, unlisted-pending, rejected, and removed content remains gated. Grant/revoke moderation with `php artisan nonogram:moderator {email} [--revoke]` and admin access with `php artisan nonogram:admin {email} [--revoke]`.

**Acceptance:** Security tests cover object-level authorization, visibility, CSRF/session routes, validation abuse, rate limiting, XSS, and answer secrecy.

## B. Accessibility and browser quality

- [~] Audit all controls with keyboard only; implement visible focus, logical focus order, labels, and non-color status cues. Editor canvas and semantic cell table support arrow navigation and fill/erase keys; player cells are roving-focus controls with explicit mark labels. Vue tests and Playwright Chromium, Firefox, and WebKit cover editor/player keyboard navigation and activation; complete a manual keyboard sweep of every page control before release.
- [~] Verify grid clues and cell states are announced meaningfully to assistive technologies; provide a non-canvas accessible interaction/view where canvas is used. The editor offers a semantic table toggle; player clues use table headers and named cell controls. Empty classic clues are explicitly announced as “empty” (rather than the visual zero marker or a blank label), with component regression tests. Manual screen-reader testing remains.
- [~] Test high contrast, reduced motion, text scaling, touch target size, landscape/portrait mobile, and virtual keyboard behavior. Reduced-motion and forced-colors focus/selection styles are implemented and emulated in Playwright; mobile viewport tests verify 44px editor/player controls and cells, and player zoom respects the mobile minimum. Manual high-contrast, zoom/text-scaling, touch, orientation, and virtual-keyboard checks remain.
- [~] Run browser tests for editor drag, touch interactions, zoom hit testing, autosave conflicts, publish failure, play/resume, and completion. Playwright Chromium, Firefox, and WebKit tests cover square player cells, keyboard operation, an emulated touchscreen tap, guest-progress resume after reload, 44px touch targets, forced colours/reduced motion, server life feedback, safe auto-cross, Hardcore, maximum-size editor rendering, drag/erase/clear, zoom hit testing, 409 save conflicts, rejected publication, and editor reload recovery; testing on physical touch devices and end-to-end auth/publish/completion remain.
- [~] Test current supported Chrome, Firefox, Safari, and mobile browsers; document unsupported APIs and fallbacks. The Playwright suite now runs in Chromium, Firefox, and WebKit on CI; WebKit is a Safari-engine proxy, not certification of current Safari/iOS Safari, Android Chrome, or Edge devices. Browser API fallbacks and unsupported baseline APIs are documented in `DOCS/SUPPORTED-PLATFORMS.md`; manual version/device certification remains.

**Acceptance:** No critical keyboard or screen-reader blockers remain; browser test suite passes on supported CI browsers.

## C. Reliability and performance

- [~] Benchmark maximum 30×30 grid encode/decode, clue generation, client rendering, and server validation; set regression thresholds. PHP grid parse/serialize/clue generation and the full draft-create validation/normalization path each have a 2-second regression test; Playwright verifies rendering all 900 accessible editor cells within 2 seconds in Chromium, Firefox, and WebKit. Manual real-device rendering/touch performance and publish-time solver measurements remain separately covered by solver work limits.
- [~] Bound solver time, recursion/iteration count, memory, and queue concurrency. The synchronous solver caps work at 1.5 seconds, 100,000 search nodes, 50,000 candidates per line, and 20,000 candidates globally; exhausted searches return `unknown`, never a false uniqueness success, with maximum-dimension tests. Queue concurrency limits remain inapplicable until solver work is queued.
- [x] Add queue/cache/Redis only when required; document local sync fallback and production worker setup if jobs are queued. No asynchronous jobs or queue-dependent features are present; the uniqueness solver runs synchronously with hard time/node/candidate limits. The deployment runbook records that no worker is currently required.
- [~] Add database indexes after checking browse/progress query plans; paginate all user-generated content lists. Local MySQL `EXPLAIN` confirms the public browse, creator profile, collection listing, and revision-progress aggregate use their composite indexes; production-scale plans and pagination review remain.
- [x] Add structured error reporting without logging canonical answers, image contents, or sensitive user data. Unhandled server exceptions are written as one JSON record per line to a dedicated `errors` channel (`storage/logs/errors-*.log`, 30-day rotation); records hold request metadata, exception class/location, and an argument-free stack summary. A redactor removes credentials, e-mail addresses, encoded answers, data URLs, tokens, clues, marks, and image payloads; database failures log the unbound SQL and SQLSTATE instead of bound values; request bodies are never captured; client errors stay out of the error log; and `X-Request-Id` correlates a response with its record. Unit/feature tests cover redaction, body/argument exclusion, database values, request-id propagation, and client-error suppression. Log shipping/alerting configuration remains a deployment task.
- [ ] Test backup and restore of database and media, including puzzle revision/progress relationships.

**Acceptance:** Resource-heavy operations have hard limits and operational failure modes are visible and recoverable.

- [~] Ensure production config/cache/route build and frontend production build pass; disable debug output and set secure cookie/HTTPS settings in deployment config. Local production-mode config, route, and view caches built successfully with `APP_DEBUG=false` and secure cookies enabled, then were cleared; host HTTPS/proxy/secrets settings still require deployment validation.
- [~] Add CI for PHP tests/format, dependency audits, TypeScript checks/unit tests, and frontend build; optionally add browser E2E suite. Cross-engine hosted validation is pending.
- [~] Define database migration rollback/forward-fix policy and release checklist; do not rely on rolling back destructive published-data changes. The deployment runbook recommends forward fixes, compatibility checks, and a pre-migration backup; a tested host-specific recovery plan remains. Before public launch, assign at least one verified moderator with the documented Artisan command.
- [x] Record supported PHP/Laravel/browser/database versions and dependency update process. `docs/SUPPORTED-PLATFORMS.md` defines PHP 8.4.1+/Laravel 13, Node 22, MySQL 8+, evergreen browser targets, monthly dependency review cadence, audits, and required checks; real-browser compatibility certification remains tracked separately.

**Release gate:** All tests pass from a clean checkout; no unresolved critical/high security issues; backup restore and solution-leakage checks verified.
